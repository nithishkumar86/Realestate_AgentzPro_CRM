# Production Login System Plan

## 1. Scope

This plan covers only the passwordless email OTP login system and the automatic creation and protection of these four application tables:

1. `public.profiles`
2. `public.tenants`
3. `public.tenant_memberships`
4. `public.tenants_subscriptions`

Supabase owns and manages `auth.users`. It is referenced by the application tables but is not created or modified directly by application SQL.

This is a multi-tenant system. One tenant must never be able to read or modify another tenant's data.

## 2. Confirmed Business Rules

- Authentication uses passwordless email OTP through Supabase Auth.
- The same verified email continues to use the same `auth.users.id` on later logins.
- A first-time owner completes onboarding after successful OTP verification.
- Owner onboarding collects:
  - Full name
  - Phone number
  - Company name
  - Professional role
- One company is represented by one tenant.
- The initial release creates one owner membership per tenant.
- The membership model remains ready for future admin and employee memberships.
- Every new tenant receives a 14-day free trial automatically.
- Subscription access states are `trialing`, `active`, and `blocked`.
- Expired trials or expired paid periods must be blocked automatically.
- The browser must never choose trusted identifiers, membership roles, subscription statuses, or subscription timestamps.

## 3. Canonical Naming

The following names are frozen for this implementation:

| Meaning | Canonical name |
|---|---|
| Supabase user identifier | `user_id` |
| Tenant identifier | `tenant_id` |
| Membership identifier | `tenant_membership_id` |
| Subscription identifier | `tenant_subscription_id` |
| Person's business/professional title | `professional_role` |
| Authorization role inside a tenant | `membership_role` |
| Subscription state | `subscription_status` |
| Timestamp columns | Suffix `_at` |

The four objects above are tables in one Supabase PostgreSQL database, not four separate databases.

## 4. Supabase Authentication Behaviour

The application calls `signInWithOtp()` to request an email OTP. For a previously unknown email, Supabase automatically signs up the user by default unless `shouldCreateUser: false` is supplied.

The OTP-send response does not contain an authenticated session. A session is created only after successful OTP verification.

Consequences for this architecture:

- Do not use the existence of an `auth.users` row as proof that onboarding is complete.
- Do not create a tenant from an `auth.users` insertion trigger.
- Start application onboarding only after OTP verification returns a valid authenticated session.
- Determine onboarding completion from the application-owned membership and related rows.

Official reference: [Supabase passwordless email login](https://supabase.com/docs/guides/auth/auth-email-passwordless)

## 5. Table Data Contracts

### 5.1 `public.profiles`

Purpose: store personal details belonging to one authenticated person.

| Column | Type | Null | Constraint/default | Source |
|---|---|---:|---|---|
| `user_id` | `uuid` | No | PK; FK to `auth.users(id)` | Verified Supabase session |
| `full_name` | `text` | No | Validated non-empty value | Onboarding form |
| `phone_number` | `text` | No | Validated and normalized | Onboarding form |
| `professional_role` | `text` | No | Validated non-empty value | Onboarding form |
| `created_at` | `timestamptz` | No | Database default `now()` | Database |
| `updated_at` | `timestamptz` | No | Database default and update trigger | Database |

Rules:

- `profiles` does not contain `tenant_id`.
- A profile describes a person. `tenant_memberships` connects that person to a tenant.
- Email is not duplicated here; `auth.users` remains the canonical email source.
- `user_id` cannot be changed through profile updates.
- Phone number is not used as the authentication identity.

### 5.2 `public.tenants`

Purpose: represent one customer company and permanently own that company's CRM data.

| Column | Type | Null | Constraint/default | Source |
|---|---|---:|---|---|
| `tenant_id` | `uuid` | No | PK; `gen_random_uuid()` | Database |
| `tenant_name` | `text` | No | Validated non-empty value | Company field in onboarding |
| `tenant_status` | `text` | No | `active`, `suspended`, or `closed`; default `active` | Database/backend |
| `created_at` | `timestamptz` | No | Database default `now()` | Database |
| `updated_at` | `timestamptz` | No | Database default and update trigger | Database |

Rules:

- `tenant_name` comes from the Company field. It is not the user's name.
- `tenant_id` is generated by PostgreSQL and is never accepted from the browser.
- Tenant suspension is separate from subscription expiry.

### 5.3 `public.tenant_memberships`

Purpose: authorize a Supabase user to belong to a tenant.

| Column | Type | Null | Constraint/default | Source |
|---|---|---:|---|---|
| `tenant_membership_id` | `uuid` | No | PK; `gen_random_uuid()` | Database |
| `tenant_id` | `uuid` | No | FK to `tenants(tenant_id)` | Onboarding transaction |
| `user_id` | `uuid` | No | FK to `auth.users(id)` | `auth.uid()` |
| `membership_role` | `text` | No | `owner`, `admin`, or `employee` | Backend; initial value `owner` |
| `membership_status` | `text` | No | `active` or `blocked`; default `active` | Backend |
| `created_at` | `timestamptz` | No | Database default `now()` | Database |
| `updated_at` | `timestamptz` | No | Database default and update trigger | Database |

Required constraints:

- `UNIQUE (tenant_id, user_id)` prevents duplicate membership.
- `UNIQUE (user_id)` enforces the initial one-company-per-user rule.
- A partial unique index permits only one `owner` membership per tenant.
- `tenant_id` itself is not unique because future employees will share the owner's tenant.

Role separation:

- `profiles.professional_role` describes the person's occupation, for example `Real Estate Agent`.
- `tenant_memberships.membership_role` controls authorization, for example `owner`.

### 5.4 `public.tenants_subscriptions`

Purpose: control whether a tenant currently has CRM access.

| Column | Type | Null | Constraint/default | Source |
|---|---|---:|---|---|
| `tenant_subscription_id` | `uuid` | No | PK; `gen_random_uuid()` | Database |
| `tenant_id` | `uuid` | No | FK to `tenants(tenant_id)` and UNIQUE | Onboarding transaction |
| `subscription_status` | `text` | No | `trialing`, `active`, or `blocked`; default `trialing` | Database/backend |
| `trial_started_at` | `timestamptz` | No | Database current time | Database |
| `trial_ends_at` | `timestamptz` | No | `trial_started_at + interval '14 days'` | Database |
| `current_period_started_at` | `timestamptz` | Yes | Required when paid access begins | Payment backend later |
| `current_period_ends_at` | `timestamptz` | Yes | Required for time-limited paid access | Payment backend later |
| `created_at` | `timestamptz` | No | Database default `now()` | Database |
| `updated_at` | `timestamptz` | No | Database default and update trigger | Database |

One tenant has exactly one subscription row because `tenant_id` is unique in this table.

CRM access is valid only when all conditions are true:

```text
tenant_status = active
AND membership_status = active
AND (
  subscription_status = trialing AND trial_ends_at > now()
  OR
  subscription_status = active AND current_period_ends_at > now()
)
```

`blocked` never grants CRM access.

## 6. End-to-End Login Pipeline

### 6.1 Request OTP

1. User enters an email address.
2. Normalize the email for the request.
3. Require a valid Cloudflare Turnstile token.
4. Apply the Upstash Redis per-email and per-IP rate limits defined in Section 10.
5. Enforce Supabase Auth's built-in OTP limits as the Auth-level backstop.
6. Continue only when the Turnstile and both rate-limit checks succeed.
7. Call Supabase `signInWithOtp()`.
8. Return a generic response that does not reveal whether the email previously existed.

No application-owned row is created at this stage.

### 6.2 Verify OTP

1. User submits email and OTP.
2. Supabase verifies the OTP.
3. Failed verification returns no application access.
4. Successful verification creates an authenticated session.
5. The backend validates the session and obtains `auth.uid()`.
6. Never accept `user_id` from the request body.

### 6.3 Resolve Login State

After verification, call a controlled login-state query using `auth.uid()`.

Possible results:

| State | Required action |
|---|---|
| No membership and no application rows | Show first-time owner onboarding |
| Complete profile, tenant, membership, and subscription | Evaluate access and route user |
| Any partial or contradictory record set | Block onboarding, record an integrity error, and require backend investigation |

The application must not repair partial data by silently creating another tenant.

### 6.4 First-Time Owner Onboarding

Collect only:

- Full name
- Phone number
- Company name
- Professional role

Call one authenticated PostgreSQL RPC function, provisionally named `complete_owner_onboarding`.

The function accepts only the four onboarding values. It derives all trusted values itself:

- `user_id` from `auth.uid()`
- `tenant_id` from `gen_random_uuid()`
- `tenant_membership_id` from `gen_random_uuid()`
- `tenant_subscription_id` from `gen_random_uuid()`
- `membership_role = 'owner'`
- `membership_status = 'active'`
- `tenant_status = 'active'`
- `subscription_status = 'trialing'`
- Trial timestamps from the database clock

Inside one PostgreSQL transaction, the function:

1. Confirms an authenticated user exists.
2. Confirms that the user does not already have a membership.
3. Inserts the profile.
4. Inserts the tenant.
5. Inserts the owner membership.
6. Inserts the 14-day trial subscription.
7. Verifies that all four application rows now form one consistent ownership chain.
8. Returns the generated `tenant_id` and the calculated access state.

If any step fails, the entire transaction rolls back. The system must never commit only some of the four rows.

### 6.5 Idempotency and Concurrent Requests

The onboarding operation must be safe when the browser retries or the user double-clicks:

- A completed onboarding call returns the existing tenant instead of creating a second tenant.
- Database unique constraints are the final concurrency protection.
- Two simultaneous requests cannot create two memberships for one user.
- Any transaction that loses the concurrency race rolls back its newly created tenant and subscription rows.

### 6.6 Existing-User Login

For every later login with the same email:

1. Supabase returns the existing user identity after OTP verification.
2. The application finds the existing membership using `auth.uid()`.
3. It does not recreate any application row.
4. It checks tenant, membership, and subscription access.
5. Valid access routes to the CRM dashboard.
6. Invalid or expired access routes to the billing/blocked page.

Authentication and authorization remain separate. A user can be correctly authenticated but still be denied CRM access.

## 7. Trial and Subscription Automation

### Immediate enforcement

Every protected CRM database operation must evaluate the subscription timestamp. This provides automatic blocking at the exact expiry time without waiting for a scheduled job.

### Scheduled reconciliation

Run an hourly Supabase Cron reconciliation job:

- Change expired `trialing` rows to `blocked`.
- Change expired `active` periods to `blocked` when renewal has not extended the period.
- Record failures for operational monitoring.

The cron maintains a clear stored status for the interface and reports. It is not the security boundary. If cron fails, timestamp-based RLS must still block access.

Payment-provider activation and webhook fields are outside this login-system plan. A future trusted payment backend may transition a tenant from `trialing` or `blocked` to `active` and set the paid-period timestamps.

## 8. RLS and Database Permissions

Enable RLS on all four public tables. Revoke all default table privileges from `anon` and `authenticated`, then grant back only the operations explicitly required below.

Official reference: [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)

### 8.1 Anonymous role

The `anon` role receives no `SELECT`, `INSERT`, `UPDATE`, or `DELETE` access to any of the four tables.

### 8.2 `public.profiles`

- `SELECT`: authenticated user may read only the row where `profiles.user_id = auth.uid()`.
- `UPDATE`: authenticated user may update only allowed personal columns on their own row.
- `INSERT`: no direct browser insert; onboarding RPC only.
- `DELETE`: no direct browser delete.
- An update must not change `user_id`.

Profile access remains available when a subscription is blocked so the authenticated user can view their account.

### 8.3 `public.tenants`

- `SELECT`: authenticated user may read only a tenant connected to their membership.
- `INSERT`: no direct browser insert; onboarding RPC only.
- `UPDATE`: no unrestricted browser update; an owner-only controlled function handles allowed company changes.
- `DELETE`: no direct browser delete.

A user may read the minimum tenant information required for the billing/blocked page even after subscription expiry. CRM data access remains blocked.

### 8.4 `public.tenant_memberships`

- `SELECT`: authenticated user may read only their own membership row.
- `INSERT`: no direct browser insert.
- `UPDATE`: no direct browser update of `tenant_id`, `user_id`, role, or status.
- `DELETE`: no direct browser delete.

The browser cannot promote a membership or move itself to another tenant.

### 8.5 `public.tenants_subscriptions`

- `SELECT`: authenticated user may read only the subscription belonging to the tenant in their membership.
- `INSERT`: no direct browser insert; onboarding RPC only.
- `UPDATE`: no browser update. Only trusted subscription/payment processing may change status and period timestamps.
- `DELETE`: no direct browser delete.

The browser cannot activate, extend, or unblock its own subscription.

### 8.6 Shared CRM-access authorization function

Implement one database authorization helper that accepts a target `tenant_id` and returns true only when:

- `auth.uid()` has an active membership for that exact tenant.
- The tenant is active.
- The tenant has a currently valid trial or paid period.

Requirements:

- Place the helper in a non-exposed schema.
- Fix the function `search_path` explicitly.
- Do not accept `user_id`, membership role, or subscription status from the browser.
- Grant only the minimum execution permission required.
- Use this helper consistently in RLS for every future tenant-owned CRM table.

## 9. Onboarding RPC Security

The onboarding RPC must:

- Reject unauthenticated callers.
- Obtain identity exclusively from `auth.uid()`.
- Validate and length-limit all text inputs.
- Normalize required values before insertion.
- Use one atomic database transaction.
- Be idempotent.
- Use `SECURITY DEFINER` only when necessary.
- Set `search_path` to an explicit safe value.
- Fully qualify every referenced table.
- Revoke function execution from `public` and `anon`.
- Grant execution only to `authenticated`.
- Never use a browser-supplied role, status, trial date, subscription date, `user_id`, or `tenant_id`.

## 10. Session and OTP Protection

- Enable Supabase CAPTCHA protection using Cloudflare Turnstile.
- Apply Supabase OTP-send and verification rate limits.
- Use Upstash Redis with `@upstash/ratelimit` for application-level OTP counters.
- Run the Upstash checks in the Next.js server route before calling Supabase `signInWithOtp()`.
- Do not call `signInWithOtp()` directly from the browser; the OTP-send request must pass through the protected server route.
- Return generic messages to prevent email-account enumeration.
- Keep Supabase secret/service-role keys on trusted backend infrastructure only.
- Use secure, HTTP-only, same-site cookies for server-rendered session handling.
- Do not use local storage as the authoritative tenant or subscription state.
- Re-evaluate authorization on protected requests; never rely only on a dashboard redirect.

### 10.1 OTP rate-limit responsibilities

The three protection layers have different jobs:

| Layer | Responsibility |
|---|---|
| Cloudflare Turnstile | Reduce automated bot requests before an OTP is sent |
| Upstash Redis | Count and limit requests for the same normalized email and source IP |
| Supabase Auth limits | Provide the final rate limit at the authentication service itself |

Upstash Redis is used for OTP rate limiting. QStash is not part of the login system and must not be used for OTP counters.

### 10.2 Required application limits

Apply all applicable limits to every OTP request:

| Counter | Recommended production limit | Action when exceeded |
|---|---:|---|
| Same normalized email cooldown | 1 OTP per 60 seconds | Reject until the cooldown ends |
| Same normalized email window | 3 OTP sends per rolling hour | Temporarily block new sends for that email |
| Same source IP window | 10 OTP sends per rolling hour | Temporarily block new sends from that IP |
| Wrong OTP verification attempts | 5 attempts per 15 minutes for the email/IP combination | Apply a 30-minute application block |

The 30-minute block is deliberate. A four-to-five-hour block would allow an attacker to create an unnecessarily long denial of service against a legitimate customer.

Supabase's own limits remain enabled. The custom limits do not replace them.

### 10.3 Redis identifier privacy

Do not place raw email addresses or raw IP addresses in Redis key names. Generate non-reversible identifiers on the server with HMAC-SHA-256 and a dedicated secret:

```text
otp:send:email:<HMAC(normalized_email)>
otp:send:ip:<HMAC(source_ip)>
otp:verify:<HMAC(normalized_email + source_ip)>
```

Requirements:

- Normalize the email consistently before generating its identifier.
- Read the source IP only from the hosting platform's trusted request metadata.
- Keep the HMAC secret in backend environment variables.
- Assign a TTL to every counter so Redis removes it automatically.
- Never send Redis credentials or the HMAC secret to the browser.

### 10.4 OTP-send decision

```text
Turnstile valid
AND email limit allows
AND IP limit allows
AND Supabase Auth limit allows
= Supabase may send the OTP
```

If any check rejects the request, do not call `signInWithOtp()` and do not create application rows.

The user-facing response must remain generic. Internal logs may record the rejection reason without storing the OTP or raw sensitive values.

Official references:

- [Supabase CAPTCHA protection](https://supabase.com/docs/guides/auth/auth-captcha)
- [Supabase Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits)
- [Supabase user sessions](https://supabase.com/docs/guides/auth/sessions)
- [Upstash rate-limit documentation](https://upstash.com/docs/redis/sdks/ratelimit-ts/overview)

## 11. Failure Handling

| Failure | Required result |
|---|---|
| OTP send failure | Create no application rows |
| Invalid or expired OTP | Create no session and no application rows |
| Onboarding validation failure | Create no application rows |
| Any database insert failure | Roll back all onboarding inserts |
| Duplicate onboarding request | Return existing completed onboarding or one controlled conflict; create no duplicate tenant |
| Partial historical data detected | Block access and raise an integrity alert |
| Trial cron failure | Timestamp-based access rule continues blocking expired access |
| Expired subscription | Authentication may succeed; CRM access is denied |
| Suspended tenant | Authentication may succeed; CRM access is denied |
| Blocked membership | Authentication may succeed; CRM access is denied |

## 12. Required Automated Tests

### Authentication and onboarding

1. A new verified user can complete onboarding once.
2. An unverified or unauthenticated caller cannot run onboarding.
3. The same email on a later login uses the existing application rows.
4. A repeated or concurrent onboarding call does not create duplicates.
5. A failure in any onboarding insert rolls back all four application rows.
6. The browser cannot supply a different `user_id` or `tenant_id`.

### RLS and tenant isolation

7. `anon` cannot read or write any of the four tables.
8. Tenant A cannot read Tenant B's profile, tenant, membership, or subscription rows.
9. Tenant A cannot update Tenant B's rows.
10. A user cannot change their membership role or tenant.
11. A user cannot activate or extend their subscription.
12. A user can update only approved fields in their own profile.
13. Direct table inserts from an authenticated browser are rejected.

### Subscription enforcement

14. A valid trial grants access before `trial_ends_at`.
15. The same trial is denied immediately after `trial_ends_at` even if cron has not executed.
16. A paid subscription is denied after `current_period_ends_at`.
17. `blocked` never grants CRM access.
18. A suspended tenant never receives CRM access.
19. A blocked membership never receives CRM access.
20. An expired user can read the minimum account/subscription information required to renew but cannot read tenant CRM data.

Create RLS allow-and-deny tests with `supabase test db`. The system is not ready for production until the cross-tenant and expiry tests pass.

## 13. Implementation Order

1. Create a migration containing the four tables, foreign keys, checks, unique constraints, indexes, and timestamp triggers.
2. Enable RLS, revoke default privileges, grant minimum privileges, and create operation-specific policies in the same migration.
3. Implement and secure the shared tenant-access authorization helper.
4. Implement the atomic, idempotent owner-onboarding RPC.
5. Configure email OTP templates and expiry.
6. Configure Cloudflare Turnstile and Supabase Auth protection.
7. Configure Upstash Redis and implement the email/IP OTP rate limits.
8. Implement OTP request and verification routes through the protected Next.js server endpoints.
9. Implement login-state resolution and the onboarding form.
10. Implement dashboard-versus-billing routing using server-verified access.
11. Configure hourly subscription reconciliation cron.
12. Add automated database, RLS, concurrency, and end-to-end tests.
13. Run production migration rehearsal and rollback testing in a staging Supabase project.

## 14. Final Ownership Chain

```text
auth.users.id
    -> profiles.user_id
    -> tenant_memberships.user_id
    -> tenant_memberships.tenant_id
    -> tenants.tenant_id
    -> tenants_subscriptions.tenant_id
```

Final authorization meaning:

```text
Supabase Auth proves who the user is.
The profile stores who the person is.
The tenant stores which company owns the data.
The membership determines which company the user belongs to.
The subscription determines whether that tenant currently has CRM access.
RLS enforces the result inside PostgreSQL.
```
